# ExposeMe device lab

Everything goes through `qa/lab/lab.sh` (run without args for help). Artifacts land in `qa/runs/` (git-ignored).

## Topology
```
 Server (ts-node, :3000) ◄── socket.io ──┬── bots (node qa/lab/bots.mjs, headless players)
 Metro  (:8081, EXPO_PUBLIC_SERVER_URL)  ├── ios-a  iPhone 17          (simctl, localhost)
                                         ├── ios-b  iPhone 16e
                                         ├── android-a exposeme_a (Pixel 7, API 35)  adb reverse :3000 :8081
                                         └── android-b exposeme_b (Pixel 4, API 35)
```
Devices reach the host through `localhost` (iOS simulators share the host network; Android uses `adb reverse`). The app is a **dev client**: JS comes from Metro, so code changes need no rebuild — only native dependency/config changes need `build`. `Client/ios` and `Client/android` are generated by `expo prebuild` (not versioned): after changing `Client/app.json`, an icon/splash image it points to (`./assets/...`), `Client/package.json` (native deps) or a config plugin (`Client/plugins/`, `app.config.*`) run `lab.sh build <platform> --prebuild` (runs `CI=1 npx expo prebuild --no-install` on the Client's Node, then builds); `build` warns when those inputs changed since the lab's last prebuild (hash per platform in `qa/runs/.lab/prebuild-hash-<platform>`, EXP-255/EXP-086) and prebuilds on its own when the native folder does not exist yet.

## First time (≈20-30 min, mostly builds)
```bash
qa/lab/lab.sh setup        # Maestro CLI, AVDs exposeme_a/b, npm deps
qa/lab/lab.sh up           # 2 iOS + 2 Android (flags: --ios N --android N)
qa/lab/lab.sh server && qa/lab/lab.sh metro
qa/lab/lab.sh build all --prebuild   # expo prebuild + dev-client binaries, installs on every device
qa/lab/lab.sh photos 12    # 12 labelled photos per device gallery + bot photos
```

## Every session
```bash
qa/lab/lab.sh up && qa/lab/lab.sh server && qa/lab/lab.sh metro
qa/lab/lab.sh open                                   # app on all devices → local Metro (Android: cold start through the link, dev menu closed)
RUN_ID=it3-EXP-006 qa/lab/lab.sh play --devices pair --bots 3 --rounds 3   # per-fix check: 1 iOS + 1 Android
RUN_ID=it9-regression qa/lab/lab.sh play --devices all --bots 3 --rounds 10 # regression: all 4 devices
qa/lab/lab.sh shot after-fix                         # screenshot every device
qa/lab/lab.sh down                                   # when finished
qa/lab/lab.sh down --worktrees                       # also stop every git worktree's own lab server (server --port N)
```
`down --worktrees` runs from the main checkout only (from a worktree it refuses: it would stop the other agents' servers). It reads each linked worktree's pidfiles (`<worktree>/qa/runs/.lab/server*.pid`, the ones `status` lists) and stops a server only if the pid still runs `ts-node server.ts` in that worktree's `Server/` dir or serves the pidfile's port; a stale pidfile (pid gone or reused by another session) is removed without killing anything (`<name>: stale pidfile removed, nothing stopped`).
`play` = bots create the room and wait for `bots + devices` players → each device runs `qa/maestro/play-game.yaml` in parallel (open → join with the code → play, tapping `bot1` as its guess and screenshotting every loop) → host bot starts → results in `qa/runs/<RUN_ID>/` (`bots.json`, `bots.log`, `maestro/<device>/…`, junit xml). A device whose flow failed while booting the dev client — stuck on "Downloading N%…" (the last failed step's screen hierarchy shows it; seen with 4 devices loading the bundle at once, EXP-256), or the `assertTrue ${output.devClientBoot.loaded}` of `dev-client-boot.yaml` FAILED in Maestro's `commands.json` (launcher, "isn't responding" dialog, or the "There was a problem loading the project" screen, EXP-297/EXP-304) — is force-stopped (`am force-stop` / `simctl terminate`) and runs the flow once more while the room still waits for it (the devices that already joined wait in the lobby with `wait-game-start.yaml`, whose ceiling `LOBBY_WAIT_MS` = 420 s is passed by `play` and covers the stuck attempt + the retry; budget in `lab.sh`): `play` logs `<device>: dev client stuck loading the JS bundle (<reason>)…` and the retry's results go to `maestro/<device>-retry/` (EXP-256, EXP-297). Only this run's hierarchies count (each device's output folder is cleared before its run, so a reused `RUN_ID` can't trigger or hide a retry). `join-room.yaml` also retypes the room code once (`type-room-code.yaml`) when the field lost it and asserts the field holds it before searching with the keyboard's Enter (Go, EXP-378; `join-unknown-room-es.yaml` taps `search-room-button` with the keyboard up instead).

Extra inputs for a flow: `--maestro-env KEY=VALUE` (repeatable) passes another variable to every device's Maestro run, and `--second-room "<bots.mjs args>"` starts a 2nd bots room first (results in `qa/runs/<RUN_ID>/second-room/`) and passes its code as `NEW_CODE`; it is stopped when the run ends and its exit status does not count. The invite-link check is one line (see the header of `qa/maestro/invite-link-after-game.yaml`):
```bash
qa/lab/lab.sh play --devices ios-a --bots 2 --rounds 3 --flow invite-link-after-game \
  --bot-args "--play-again-linger 60 --play-again-linger-bot 0" --second-room "--bots 3 --host --wait-players 5 --timeout 900"
```
The kicked-player notice (EXP-139/EXP-045, `qa/maestro/kicked-notice.yaml`): one bot hosts, the device joins and the host bot removes it by its label (its username in the room) 5 s later; the device must land on the home screen with "The host removed you from the room." / "El anfitrión te ha sacado de la sala.", and the bots run ends right after the kick (reason `lobby-kick`). After joining again by hand, the flow exits with the close button: home's form must be back (join panel closed) and, on Android, Back must leave the app, with no second home under it (EXP-339, checked by `lab-play.test.sh`):
```bash
qa/lab/lab.sh play --flow kicked-notice --bots 1 --devices ios-a --bot-args '--kick ios-a'
```
Kicked after the game (EXP-337/EXP-346): the device plays a 3-round game and the host bot removes it 120 s after game over (`--kick-after-game 120`; the bots stay on their final screens and end right after the kick, the room stays). `kicked-after-game` waits on the final ranking for the translated notice; `kicked-while-offline` kills the app on the final ranking, so it misses the kick, then reopens it and joins again by hand: its stored rejoin token is refused and it gets the same notice. Both then join by hand once more and must land in the lobby as a new player (the token was forgotten):
```bash
qa/lab/lab.sh play --flow kicked-after-game --bots 2 --rounds 3 --devices ios-a --bot-args '--kick ios-a --kick-after-game 120'
qa/lab/lab.sh play --flow kicked-while-offline --bots 2 --rounds 3 --devices ios-a --bot-args '--kick ios-a --kick-after-game 120'
```
A flow that a second device breaks (leave-paused-game: two players stay connected and nothing pauses; the kick flows, tie-game, lobby-host-drop, invite-link-mid/after-game) says so in its header, `# lab: one device (<why>)`, and `play` refuses it on more than one device before starting any bots (EXP-389): pick one with `--devices <label>`. Mark a new flow the same way when that holds for it.

The device as the host (EXP-390, `qa/maestro/device-host-start.yaml`): `play --device-host` lets the one selected device create the room. Its flow reads the code from the lobby and POSTs it with Maestro's `http` to a listener `play` starts on loopback (`CODE_SINK_URL`; it takes only a room code of the server's alphabet and length, and keeps the first one). Then the bots join with `bots.mjs --code`. The device opens the remove-player confirmation on bot3 («…@bot3…?» in en|es), cancels it, removes bot3, taps Start (the optional, short look for «Starting…|Empezando…» is WARNED when it misses that ~0.5 s window, which is not a failure) and plays the lobby's default 10 rounds to the end. Constraints: exactly one device, the shared server :3000 (no `--server`/`--port`), no `--rounds`, at least 3 bots and no `--name-prefix` in `--bot-args`. A flow that ends or times out without posting fails the run and is stopped with its Maestro children, and a hosting flow that fails stops the bots instead of waiting them out. The plumbing is checked without devices by `qa/lab/tests/lab-device-host.test.sh` (stub bots/maestro, real listener):
```bash
qa/lab/lab.sh play --device-host --flow device-host-start --devices ios-a --bots 3
```

`--rounds` takes 10/15/20, or 3 for short QA runs (~1 min): 3 is QA-only, accepted only because `lab.sh server` starts the server with `ALLOW_QA_ROUNDS=1` (a server started another way, or production, ignores it and the bots report a `game-started with 10 rounds, asked for 3` consistency error). The app never offers 3 rounds.

## Why the photos are labelled
`make-photos.swift` stamps `IOS-A · #3`, `ANDROID-B · #7`, `BOT · #2` on each picture. In a screenshot you can see whose gallery the photo came from and check it against the revealed owner — a direct test of the "who's photo" logic and of cross-device sync.

`photos [N]` is idempotent (re-running it never stacks a 2nd copy of the same labels):
- Android: files are named `exposeme-lab-<label>-NN.jpg` in the lab-only `/sdcard/Pictures/ExposeMeQA`; each run deletes the folder's previous `*.jpg` files (also the ones named before the prefix), pushes the new ones and rescans MediaStore. Nothing outside that folder is touched.
- iOS: `simctl addmedia` can't delete and renames imports to `IMG_NNNN`, so after seeding the lab writes `exposeme-lab-seeded` (`<label> <count>`) into the simulator's `data/Media` folder. Later runs skip the simulator, or add only the missing numbers when N grows. Erasing the simulator removes the marker too.
- `photos [N] --reset` wipes first: the Android lab folder, and on iOS the simulator's whole photo library (shutdown → delete `data/Media/DCIM` + `data/Media/PhotoData` → boot; ALL photos on that simulator; the id must be a simulator UUID with a `device.plist`, and a failed boot/import stops `photos` without writing the marker). Use it once on simulators seeded before this marker existed (duplicates), after deleting photos by hand, or to shrink N. Every wipe is logged per device (`<label>: --reset: …`: Android folder deleted; iOS shutdown, library deleted, simulator rebooted).

### Large and rotated photos (`--edge`, EXP-083)
The default galleries hold 1080×1440 portrait photos only. `photos [N] --edge` also adds three synthetic edge-case photos (gradient + drawing, no network, no real pictures) to every device gallery and to the bots' upload folder, named `exposeme-lab-<label>-edge-<kind>.jpg` (`make-photos.swift --edge <dir> <label> [prefix]`):
- `big-portrait` 3024×4032 and `big-landscape` 4032×3024 (12 MP, larger than the app's 1600 px upload size);
- `exif-rotated`: pixels stored sideways (4032×3024) with EXIF `Orientation=6`, so it is upright (3024×4032) only when the viewer applies the tag.

Each one reads `<LABEL> · EDGE`, its kind and its upright size, with `▲ TOP ▲` / `▼ BOTTOM ▼` marks, a big up arrow, a circle and a square grid: on screen the arrow must point up and the text be level (orientation), the circle stay round and the cells square (no stretching). Android pushes them with the numbered photos (a later run without `--edge` drops them); iOS imports them once (marker `exposeme-lab-seeded-edge`) and keeps them until `--reset`. The flag is opt-in so the default seeding stays fast.

Device check (few numbered photos so the random pick lands on the edge cases most rounds; the bots' edge photos go through the server's sanitizer instead of the app's resize):
```bash
qa/lab/lab.sh photos 1 --edge --reset
RUN_ID=edge-photos qa/lab/lab.sh play --devices all --bots 2 --rounds 3
qa/lab/lab.sh photos 12 --reset      # back to the normal galleries afterwards
```
Then look at the round screenshots in `qa/runs/edge-photos/maestro/<device>/`: every `… · EDGE` photo, from a phone (`IOS-A`, `ANDROID-B`, …) or a bot (`BOT`), must be upright on all four devices.

## Parallel fixers (git worktrees)
Each worktree runs its own server for bots: `qa/lab/worktree-setup.sh <worktree>` once, then from the worktree root `qa/lab/lab.sh server --port 3101` … `--stop --port 3101`. The devices, Metro (:8081) and the main server (:3000) belong to the main checkout and are used only after changes are merged into `qa/loop`.

`play --port 3101` (or `--server http://localhost:3101`) runs a bots-only game against that server: both bots rooms (`--second-room` too) and the render-skew reading (`telemetry-3101.jsonl`) use it. Only local lab servers are accepted (never production), and `--bot-args`/`--second-room` may not pick a server themselves (`--server`, `SERVER_URL=`); `bots.mjs` itself also exits 2 for a `--server`/`$SERVER_URL` that is not loopback (localhost, 127.x, [::1]). Devices and Metro can't follow (they always point at :3000), so `play` warns when devices are selected: use `--devices none`, e.g. `RUN_ID=fix-EXP-123 qa/lab/lab.sh play --port 3101 --devices none --bots 3 --rounds 3`.

## Bots alone (fast, no devices)
```bash
node qa/lab/bots.mjs --bots 4 --host --rounds 10 --photos qa/runs/photos/bots --out qa/runs/x/bots.json
node qa/lab/bots.mjs --bots 5 --host --chaos 0.15 --upload-fail 0.15     # reconnects + skipped uploads
node qa/lab/bots.mjs --rooms 20 --bots 4 --host                            # load: 20 parallel games
node qa/lab/bots.mjs --bots 3 --code K7MQ4X                                # join a room a device created
node qa/lab/bots.mjs --bots 2 --code K7MQ4X --name-prefix b-               # 2nd bots process in a room: b-bot1, b-bot2
node qa/lab/bots.mjs --bots 4 --host --rounds 3 --leave-round 2            # the last bot leaves (leave-room) at round 2
#   a "never got player-left" failure (mostly with 2 players) is the known app bug EXP-254 (leave-room lost when emitted and disconnected in the same tick), not a new regression
node qa/lab/bots.mjs --bots 4 --host --rounds 3 --kick bot4                # the host removes bot4 in the lobby (lobby only, EXP-316: NAME@R exits 2)
node qa/lab/bots.mjs --bots 3 --host --rounds 10 --hold 0.5 --chaos 0.3     # owners hold the scoreboard; under chaos a holder drops or rejoins on a new socket instead of letting go
node qa/lab/bots.mjs --bots 3 --host --rounds 3 --emoji-rate 4             # every bot sends 4 emojis/s in reveal + scoreboard (max: the server's 4/s per socket; summary emojis_sent/emojis_received)
#   render cost of emojis (EXP-400): compare `play --devices pair --bots 3 --rounds 10` with and without --bot-args "--emoji-rate 4" (device render skew, smoothness)
node qa/lab/bots.mjs --help                                                # every option (no network); unknown options exit 2
```
Summary fields: `pass`, `skew_ms` (spread between players receiving the same phase event), `answer_phase_overrun_ms` (server timer accuracy: how late round-reveal arrives after the real answer timer, i.e. the announced `duration` plus the 800 ms `ANSWER_GRACE`; ~0-30 ms is healthy), `upload_ms`, `rounds_skipped`, `holds` (scoreboard holds the server accepted from bots, `--hold`), `hold_release_ms` (per player, how long after the holder let go, left, dropped or rejoined, or the server ended the hold, it got hold-end/hold-resume; over 1 s is a consistency error), `consistency_errors` (different payloads per player, owner ≠ revealed answer, round gaps, a player who left or was removed still in lists/scores/answers, a hold not released for everyone at once). The checks live in `qa/lab/bots-analysis.mjs` (one `check*` per scenario); `qa/lab/tests/bots-analysis.test.sh` replays anonymised recorded runs (`qa/lab/tests/fixtures/bots-analysis/`) and requires the same summary, so a change that alters the output on purpose regenerates the affected fixture's `expected` and says why.

**Device render skew** (EXP-012): bots only measure when the server *sends* a phase. The lab Metro builds QA clients (`EXPO_PUBLIC_QA=1`, development bundles only) that send `qa-ack` once each phase is rendered, and the lab server (`QA_TELEMETRY=1`) appends one line per ack to `qa/runs/telemetry.jsonl` (`telemetry-<port>.jsonl` for `--port` servers; each server start moves the previous file to `.prev`). After the bots summary, `play` prints `device render skew` (per phase: `instances`, `p50`/`p95`/`max` ms of the spread between devices rendering the same round + phase) and saves it as `qa/runs/<RUN_ID>/render-skew.json`, plus that game's raw `qa-ack` rows as `qa/runs/<RUN_ID>/telemetry.jsonl` (EXP-319: the server's file is rotated on its next start, so per-round distributions stay available); nothing is printed or saved when no QA build played (e.g. `--devices none`). QA builds also send `qa-photo-shown` when the round photo first draws (EXP-395), and `render-skew.json`'s `photoVisible` gives per platform the time from the answering paint to the photo on screen (`n`, `p50`/`p95`/`max` ms), the photos that failed to draw (`failed`) and the painted rounds that never showed one (`missing` when the device stayed on the round until its reveal or scores, `missingLeft` when its screen left or it may have been offline first: no warning); a p95 above 3 s, or any failed or `missing` photo, goes to `warnings` and is printed as `WARN photoVisible …` on stderr. Restart server and Metro once after updating so both pick up the flags. By hand: `node qa/lab/render-skew.mjs qa/runs/telemetry.jsonl <ROOM_CODE>`.

## Raw device control (when Maestro is not enough)
- iOS: `xcrun simctl io <udid> screenshot f.png`, `xcrun simctl openurl <udid> <url>`, `xcrun simctl addmedia <udid> *.jpg`, `xcrun simctl privacy <udid> grant photos com.socketNull.ExposeMe`, logs `xcrun simctl spawn <udid> log stream --predicate 'process == "ExposeMe"'`.
- Android: `adb -s <serial> exec-out screencap -p > f.png`, `adb -s <serial> shell input tap X Y`, `adb -s <serial> logcat -s ReactNativeJS`.
- Maestro on one device: `~/.maestro/bin/maestro --device <id> test qa/maestro/<flow>.yaml -e USERNAME=x -e GAME_CODE=K7MQ4X -e METRO_URL=http%3A%2F%2Flocalhost%3A8081`. Interactive selector help: `maestro studio`.
- Device ids/labels: `qa/runs/.lab/devices.json`.

## Troubleshooting
- App shows "Could not connect to development server": `lab.sh metro --restart`, then `lab.sh open`; on Android re-run `adb reverse` (`lab.sh up` does it).
- Gallery empty in app: re-run `lab.sh photos` (`--reset` if the iOS marker says it is seeded but the photos are gone); on Android check `adb shell ls /sdcard/Pictures/ExposeMeQA` and the media scan.
- Same photo shows up twice / duplicate labels in a gallery: `lab.sh photos 12 --reset` once.
- `install` (also run by `build`) tries every device, prints `<label>: simctl/adb install FAILED` for each failure and exits non-zero naming them (`install failed on: …`); a platform with no build yet is reported as `skipped`, not installed.
- Permission screen loops: iOS `simctl privacy … grant photos`, Android `pm grant … READ_MEDIA_IMAGES` (done by `up`/`install`).
- Maestro can't find an element: flows select by testID (`Client/app/utils/testIds.ts`, `id:` selectors); check the id in `maestro studio`.
- iOS simulators are shown in DeviceHub (Xcode 27 replaced Simulator.app; `lab.sh up` opens it). `lab.sh shot` takes screenshots.
- `metro`/`build`/`doctor` fail with "Client needs Node N": install the major pinned in `Client/.nvmrc` (`nvm install N`); the lab picks it from nvm or Homebrew `node@N` when the default node differs.
- iOS "Cannot find native module …": `lab.sh build ios` re-runs `pod install` whenever `Client/ios/Podfile.lock` differs from `Pods/Manifest.lock` or `Client/package*.json`/`Podfile` changed after the last install. Config-plugin/`app.json` changes need `lab.sh build ios --prebuild` (`build` warns when they are pending).
- Lab helper tests (no devices): `qa/lab/tests/lab-functions.test.sh` (toolchain helpers, `install` failure reporting, `open` booting like `dev-client-boot.yaml`, `build --prebuild` and the prebuild-inputs hash; stub node/maestro), `qa/lab/tests/bots-cli.test.sh` (bots.mjs command line: `--help` and bad arguments, `--name-prefix`/`--leave-round`/`--kick` included, exit before any network activity), `qa/lab/tests/bots-analysis.test.sh` (bots summary unchanged on recorded runs; leave/kick and hold checks on synthetic games), `qa/lab/tests/render-skew.test.sh` (render-skew summary from telemetry lines, `play`'s skew print, server/Metro telemetry flags and file rotation), `qa/lab/tests/stats.test.sh` (shared nearest-rank percentile in `qa/lab/stats.mjs`), `qa/lab/tests/maestro-timing.test.sh` (static step budget of the Maestro flows inside the server's timed phases; `play-rounds.yaml`'s scoreboard bounds checked against the phase durations in `GameEngine.ts`, and the flow played by `maestro-sim.mjs` on a fake game with slow, fixed and seeded random screen reads that see the screen as they start, as they end or anywhere along them (EXP-322): every guess in time (round 1's too, also when the lobby wait ends after its options showed, EXP-326), no scoreboard check after its scoreboard closed with reads seen as they start, and no false failure in any profile (EXP-353), also with the phases painted late as it166's render telemetry measured (EXP-349: options up to 2.2 s, the rest up to 0.5 s); read profiles: random 0.6-2 s and 0.6-3.5 s, and fixed 1.8, 2 and 2.2 s (it166's slow Android). Per profile, a missing card or the device's own name on one round (2-5) must fail that run in a minimum share of games (fixed 1.8-2.2 s: at least 85 %, measured ~93-100 % over 400 games; 0.6-3.5 s: the flow seldom can tell, so the bound there is on failing or warning, at least 90 %), and on every round in nearly every game, EXP-312; phones too slow to check (fixed 3.5 and 4 s, random 2.5-4 s) never fail in the flow, nor in lab.sh with fixed reads (at most 2.5 % of the games with random ones), and a card missing on every round still fails or warns; with bot holds too (up to three a round, bots.mjs's own delays, EXP-355): no failed run, only seen holds counted as held (EXP-325) and, in every profile, a scoreboard counted as checked only when a read proved it (EXP-350: the card seen with a name that is not the device's; short holds and checks that read a held screen never count); `SIM_GAMES=400` plays 400 games per profile for rarer outcomes and `SIM_SEE_SEED=<n>` draws other read points, e.g. `SIM_GAMES=400 node qa/lab/tests/maestro-sim.mjs rounds qa/maestro/play-rounds.yaml Client/app`. Scenario `hold` plays `hold-used-up.yaml` (EXP-361) on a fake 10-round game where the device owns about a third of the rounds, with fixed reads of 0.3-4 s and random 1-4 s, the three read points and its scoreboard's events painted up to 0.5 s late, against the correct app and two broken ones (the button greys out only at hold-closed; a 4th press holds): it never passes on those, every pass on the correct app is proven, it fails there only as unchecked, and each line states its pass rate: it passes only with reads of 0.4 s or less, with 0.5 s or more (the slow emulator) every own scoreboard is late and the run ends unchecked).
- Flow steps that must land inside a game phase go between `# ── timed: <phase> ──` and `# ── end timed ──` (phases `answering`, `scores`). `maestro-timing.test.sh` allows at most 3 steps in `answering` and 4 in `scores` there (`evalScript` and a `runFlow` whose `when` is only a `true:` script are not counted, the steps inside it are). It also rejects settle waits, screen conditions (`when` visible/notVisible/platform), `repeat` other than a poll loop (EXP-353: a `while` that is only a `true:` script bound by `Date.now()`, holding only inline `runFlow` looks and `assertTrue` scripts; counted as one step), `runFlow` of a subflow file, bare `assertNotVisible` (use `extendedWaitUntil notVisible` with a short timeout), text selectors (inline ones too) and taps/swipes without `waitToSettleTimeoutMs` ≤ 500 in those blocks, and warns on `optional: true` steps. The reason: a slow Android emulator takes 1-4 s per screen read, while the options are up for 8 + 3 s and the scoreboard for 5 s. `play-rounds.yaml` checks each scoreboard at the start of the next loop pass, only between bounds taken from its wait for the options (`closesAfter`/`closesBy`); a round whose options were already up gets no scoreboard checks. Each pass ends with one look for the game over that also waits out the round photo's spinner (EXP-119; a photo still loading ends the loop and fails the wait for the game over after it), and the loop's condition is a script, so nothing reads the screen between the lobby and round 1's first look for the options (EXP-326). A Maestro read may see the screen anywhere along it and a phone may paint the options up to `optionsLagMs` late (EXP-349), so a scoreboard can slip past every read: the card wait polls with looks (first for the round's answering still on screen, then for the card) and fails only when some look surely read the scoreboard without its card (EXP-353); a scoreboard it can't tell goes unchecked. `play` prints `<device>: <checked>/<shown> scoreboards checked (<cards> with their card seen), <held> held`, where checked means a single read after the card and name checks saw the card with a name that is not the device's (EXP-350: a check that something is absent passes on a held screen too), so a low checked count on a slow phone is expected and no failure; it warns `<n> scoreboard(s) waited for without seeing the card or the held marker` (a phone too slow to tell, or the card missing on that round), and fails the run with `NONE CHECKED` when a device's card waits saw no card (cards seen minus held: 0) and found no scoreboard held after at least `NONE_CHECKED_MIN_WAITS` (2) card waits (a card missing on every round). With no card seen it only warns when some were held, when fewer card waits ran (`no scoreboard reached in time: phone too slow to check` for none: a phone that slow never reaches the card wait's guard) or when Maestro already failed that device. Holds can be combined with device games (`play --bot-args "--hold 0.5"`, EXP-325): while the photo owner holds the scoreboard the app shows only the photo and the invisible `game-held` marker; the card wait also ends on the marker, and once the scoreboard should have closed (`closesBy` + 2 s) a look for the marker counts the hold as held instead of checked and waits it out (up to the 30 s hold budget). No step fails on a hold: with `--test-output-dir` Maestro dumps the screen hierarchy and takes a screenshot for every failed or warned step, one more slow read (`maestro-sim.mjs` models it). A hold already over by that look goes uncounted. Maestro shortens a `when` look by the time since the last command that may have acted on the device, an `evalScript` included (7 s after it, a single read), so that flow keeps its bookkeeping out of `evalScript` where a look follows (read from Maestro 2.11.0's bytecode: `play` and `doctor` warn on any other version).
